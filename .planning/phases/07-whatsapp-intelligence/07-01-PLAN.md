**SecurityConfig update** — Add `/api/v1/webhooks/whatsapp` to `permitAll()` in the existing SecurityConfig.java. This is the explicit exception to the `@PreAuthorize` rule per D-06. The endpoint validates via HMAC signature (D-07), not JWT.

**WebhookSecurityConfig** — Create a separate `@Configuration` class that defines a `webhookHmacSecret` bean reading from `NUTRIAI_WEBHOOK_SECRET` env var. This keeps webhook security concerns separated from general app security.

**HmacVerificationService** — Service that:
- Takes raw request body bytes + the `X-Hub-Signature-256` header value
- Computes HMAC-SHA256 of the body using the shared secret
- Compares with timing-safe comparison (not `String.equals` — prevents timing attacks)
- Returns `true`/`false`
- If the secret is not configured (dev/test), log a warning and return `true` (permissive mode for local dev)
- Per D-07: reject and log invalid signatures

**PhoneNormalizationService** — Service that normalizes Brazilian phone numbers per D-14:
- Strip leading `+55` or `55` prefix
- Keep DDD (2 digits) + number (8-9 digits) → e.g., "11999887766"
- Strip spaces, dashes, parentheses
- Return the normalized string
- If the number is not a valid Brazilian mobile format, return empty Optional

**WebhookService** — Core service that processes incoming webhook payloads:
- Accept WhatsAppWebhookDTO (deserialized from Evolution API format)
- Look up `Patient.whatsapp` via PhoneNormalizationService: normalize the sender, query `PatientRepository.findByWhatsapp(normalizedPhone)`
- If patient found: set `patientId` and `nutritionistId` (from patient's nutritionist) on the WhatsAppMessage
- If no patient found: save the message with `patientId=null`, `nutritionistId=null`, `processed=true` (mark as processed since no action needed per D-16 "no response" or "generic response" — implementer's choice)
- Deduplicate by `messageId` — if already exists, skip processing (idempotency)
- Persist WhatsAppMessage entity
- Enqueue message ID to Redis via MessageQueueService for async processing
- Return immediately (200 OK) — the actual AI processing happens async per D-08

**MessageQueueService** — Redis-backed async processing service per D-08, D-09:
- Use `RedisTemplate<String, String>` with a `whatsapp:process` list (LPUSH/RPOP pattern)
- `enqueue(UUID messageId)` — pushes message ID to Redis list
- `dequeue()` — pops next message ID, returns Optional<UUID>
- `markProcessed(UUID messageId)` — updates WhatsAppMessage.processed = true, processedAt = now()
- Abstract the queue behind an interface (`MessageQueue`) so the provider can be swapped (D-09 requirement)
- Use `@Scheduled(fixedDelay = 2000)` polling in a `@Component` worker class that dequeues and delegates to a `MessageProcessor` interface (implemented in Plan 02 by the LLM service)
- For now, the worker just logs dequeued message IDs and marks them as processed — actual AI processing is Plan 02's responsibility
- Queue depth monitoring: log WARN if queue depth > 100
