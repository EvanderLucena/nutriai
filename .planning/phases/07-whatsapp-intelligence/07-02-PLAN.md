**LlmService** — Provider-abstracted interface per D-02:

```java
public interface LlmService {
    /**
     * Send a chat message and receive a response.
     * Single call per message — handles both classification and response/extraction (D-01).

    /**
     * Check if the LLM service is available.
     */
    boolean isAvailable();
}

**OllamaCloudLlmService** — Concrete implementation using Ollama Cloud REST API per D-02:
- Inject config: `NUTRIAI_LLM_BASE_URL` (default: `https://api.ollama.com/v1`), `NUTRIAI_LLM_MODEL` (default: `glm4`), `NUTRIAI_LLM_API_KEY`
- Use Java's `HttpClient` (java.net.http) for HTTP calls — no extra dependency needed
- POST to `/chat/completions` with OpenAI-compatible payload: `model`, `messages` (system + user), `temperature`, `max_tokens`
- Parse response: extract `choices[0].message.content` as the response text
- Timeout: 30 seconds for the HTTP call (LLM responses should come within this)
- If the call fails (timeout, 5xx, network error): log error, return `LlmResponse.failed()`
- **Provider swap** per D-02: changing provider requires only config changes (base URL, model name, API key) — no code changes. The interface stays the same.

**LlmRequest** — DTO carrying:
- `systemPrompt` (String) — The system prompt with context
- `userMessage` (String) — The patient's message
- `temperature` (double, default 0.3) — Low temperature for consistent extraction
- `maxTokens` (int, default 1000) — Enough for extraction + response

**LlmResponse** — DTO carrying:
- `content` (String) — The model's response text
- `intent` (LlmIntent enum) — Classified intent: MEAL_REPORT, PLAN_QUESTION, GREETING, MISCELLANEOUS
- `extraction` (ExtractionResult, nullable) — Structured meal data if intent is MEAL_REPORT
- `success` (boolean) — Whether the LLM call succeeded
- `errorMessage` (String, nullable) — Error details if failed

**ExtractionResult** — DTO for structured meal extraction per D-05:
- `mealLabel` (String) — e.g. "almoço", "lanche da tarde", "jantar"
- `items` (List<ExtractionItemResult>) — Food items with name, estimated quantities, estimated macros
- `extractionRaw` (String) — The original patient message text

**ExtractionItemResult** — Each extracted food:
- `name` (String) — e.g. "arroz integral", "frango grelhado"
- `grams` (Double, nullable) — Estimated portion in grams
- `kcal` (double)
- `prot` (double)
- `carb` (double)
- `fat` (double)

@Service
public class ConversationService {
    // Injected: LlmService, ExtractionService, EvolutionApiService,
    //           WhatsAppMessageRepository, WhatsAppResponseRepository,
    //           PatientRepository, EpisodeRepository

    public void processMessage(UUID messageId) {
        // 1. Load WhatsAppMessage by ID
        // 2. If patientId is null → unknown sender → no response (D-16)

        // 3. Load Patient and Nutritionist
        // 4. Check if this is the first message from this patient (no previous WhatsAppMessage with this patientId)
        //    If first → use greeting prompt (D-17)

        // 5. Classify intent and determine prompt:
        //    a. If messageType is "audio" or "image" → acknowledgment prompt (D-05)
        //    b. If messageType is "text" → classify via LLM
        //       - If meal report keywords detected → meal extraction prompt with patient context (D-03)
        //       - If plan question detected → plan question prompt with full plan context (D-03)
        //       - Otherwise → generic helpful response

        // 6. Call LlmService.chat() with appropriate prompt (single call per D-01)

        // 7. If intent is MEAL_REPORT and extraction has items:
        //    → Call ExtractionService.extractAndSave(...)

        // 8. Save WhatsAppResponse with response text and type

        // 9. Send response via EvolutionApiService.sendMessage()

        // 10. Mark WhatsAppMessage as processed
    }
}
```

The intent classification happens in the same LLM call as the response generation — no multi-step pipeline (D-01). The system prompt instructs the model to both classify (output includes intent) and respond.

**MessageProcessorWorker** — Dequeues messages from Redis and processes them:

```java
@Component
@Scheduled(fixedDelay = 2000)  // Poll every 2 seconds
public class MessageProcessorWorker {

    private final MessageQueueService messageQueueService;
    private final ConversationService conversationService;

    @Scheduled(fixedDelay = 2000)
    public void processNextMessage() {
        Optional<UUID> messageIdOpt = messageQueueService.dequeue();
        if (messageIdOpt.isEmpty()) return;

        UUID messageId = messageIdOpt.get();
        try {
            conversationService.processMessage(messageId);
        } catch (Exception e) {
            // Log error, don't crash the worker
            // Message stays marked as unprocessed (processed=false)
            // Can be retried manually or via a dead-letter mechanism (v2)
            log.error("Error processing message {}: {}", messageId, e.getMessage(), e);
        }
    }
}
```

The worker is intentionally simple: poll Redis, delegate to ConversationService, handle errors gracefully. This keeps the architecture simple for v1 (D-09 — Redis as queue, no dead-letter).

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-07 | Spoofing | LLM API calls | mitigate | API key authentication on all LLM calls (NUTRIAI_LLM_API_KEY) |
| T-07-08 | Information disclosure | Patient data in prompts | mitigate | Send minimal context per D-03: only objective + extras for meal reports, full plan only on plan questions. Never send all patient data |
| T-07-09 | Tampering | LLM extraction data | accept | AI-generated macros are estimates. Nutritionist can correct post-hoc (D-12). Marked as AI-extracted transparently |
| T-07-10 | Denial of service | LLM API timeouts | mitigate | 30s timeout on HTTP calls. Failed calls logged, message stays unprocessed for retry. Worker doesn't crash |
| T-07-11 | Elevation of privilege | Prompt injection | mitigate | System prompt instructs AI to only discuss nutrition and meal plan topics. No command execution or data access beyond meal context |
| T-07-12 | Repudiation | Response tracking | mitigate | Every AI response is persisted as WhatsAppResponse with nutritionistId and patientId |
